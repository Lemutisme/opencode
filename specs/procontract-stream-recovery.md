# Interrupted tool input diagnostics

This candidate changes one failed-input boundary in native SessionRunner. When a provider turn ends before it emits a tool-call event, the runner already flushes the retained argument text to a durable `session.next.tool.input.ended.1` event and fails the pending tool. Its projected failure previously discarded the raw string from the tool input and exposed only a generic interruption message. Subsequent provider requests therefore lacked even the size and JSON validity of the failed arguments.

After that existing EOF, provider-error, stream-failure, or interruption boundary, the pending tool failure now states that the tool was not executed locally, reports the retained UTF-8 byte count, and distinguishes complete JSON without a completed call from text that is incomplete or malformed. A longest identical-character run of at least 1,024 Unicode code points adds its length and share of the retained text, with a conditional suggestion to generate repetitive data using code. Large file content may instead be split into smaller writes. The repetition threshold controls only this post-failure diagnostic; no amount or kind of argument text triggers early interruption.

The diagnostic contains no argument excerpt, task identifier, inferred intended answer, or invented evidence file handle. Full raw text remains in the original durable event. The existing projected failed-call input remains `{}` so invalid JSON is not fabricated as a valid call and a large repetitive string is not copied back into every provider request. This does not provide model-side access to raw event evidence. Pending input left by a prior process receives the same factual description using the text actually retained; running tools keep their original interruption error because they may already have side effects. The statement is explicitly about local execution: absence of a call event cannot establish what a remote provider-hosted tool did.

Healthy tool execution and output, already-called tools, provider-managed results, regular system context, tool definitions, Contract admission and delivery, provider turn accounting, the 900-second turn limit, and the original Contract deadline retain their current behavior. The existing runner and Contract scheduler decide whether another provider turn is appropriate; the diagnostic creates no execution loop or automatic replay. Raw JSON parsing and repetition analysis occur only when describing an uncalled tool after the provider stream has ended.

The earlier terminal-feedback combination is not promoted. This candidate does none of those things.
