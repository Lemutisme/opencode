## 2. 机制正确、执行可靠、方法有效，是三个问题

| 层          | 要回答的问题                                         | 当前证据能说明什么                                                 |
| ----------- | ---------------------------------------------------- | ------------------------------------------------------------------ |
| 规范 kernel | 谁能行动、什么责任未清偿、谁能验收、哪个产物被验收？ | partial score 不被写成 discharge；授权、deadline、验收身份保持明确 |
| 执行与测量  | 实际进程是否能继续、停止、隔离和留下可核验结果？     | 修复已通过原生资格；新 cohort 已产生真实官方成绩及清理回执         |
| 求解方法    | 下一步该查什么、如何修复、重放什么、何时提交？       | 当前六段方法尚未证明比 R2 更强，首轮两个已配对实例出现退步         |

脚本化 provider 的 1,012 次请求证明次数边界、连续性和真实工具链的能力，不能证明
Luna 会正确选择实验、消费旧证据或修复程序。全仓检查通过也不能回答这个性能问题。
用户要求通过 ProgramBench 实例验证，必须以实际模型和官方评分补上这一层。

两个方法在同一 kernel 上得分不同，不能把差距直接归因于规范 reducer。当前实验
衡量的是整个固定指令方法的干预；它也没有单独识别某一段 frontier 指令的效果。

## 3. 大道至简，不等于把方法压缩到最短

**最小 kernel 与足够具体的工作方法并不冲突。**

应该删去的是多余状态、重复编排、隐式权限和不可核验的完成判断；不应只为了短而
删除能约束下一步行动的知识。R2 的成功之处不能只保留成“重视证据、认真测试”等原则。
需要保留可执行的关系：重要未决观察如何决定下一项实验或修复，怎样重放原调用和受
影响的控制，哪些已有证据仍能支持当前产物，什么才支持停止。

因此，R2 仍是需要保留的强方法基线。`ProContractTask` 本来就显式接收固定 `method`；
承载 R2 方法不需要把 benchmark 策略塞入纯规范 reducer。不能因为六段方法更简洁，
就自动认定它应替代 R2，更不能把分支命名当成胜负证据。

但**“压缩丢掉了操作细节，因而导致这次退步”仍是假设，不是已证明的原因**。
模型随机性、任务适配及完整方法中其他指令差异也可能解释结果，须由固定重复和进一步
对照区分。不要把当前负结果升级成对所有短方法的否定。

## 4. 证据能被回读，不等于证据真的在约束行为

原生资格证明旧字节在输出淘汰、checkpoint 和新 Session 后仍可找回；它没有证明
真实模型会在正确时刻去读，也没有证明修复后会重新跑原反例。

本轮结束后的公开轨迹审计应检查可观察行为，而不是推测模型内心：

- 已出现的具体差异是否保留了调用、环境和可得输出？摘要是否只作为索引？
- 修复后是否重放原反例及受影响的旧通过项？见证对应的是哪个版本的产物？
- 新 Session 是否恢复了仍重要的工作事实，还是重复遗失过的探测？
- 提交时是否还有**已观察且可行动**的未决差异？不能仅凭私有测试未满分就断言过早停止。

目前尚未据这些指标完成本 cohort 的行为归因，不能声称已经证实“Core 忘记证据”或
“R2 覆盖更全”。若之后需要显式 working frontier，先提出可反驳的最小反例；模型写出
`resolved` 不是关闭责任的权威，hash 也只证明字节身份，不证明语义覆盖。

## 5. 修复执行故障，是比较的前提，不是性能结论

NUL 启动错误、拒绝误分类、缺失的 grader 清理语义和过期凭据，曾让旧研究在取齐
证据前停止。修复它们避免把进程挂住、HTTP 200 错误流或“未启动 grader”混为任务得零分。
这些是必要的执行边界，不能拿来抵消新 cohort 中真实的分数退步。

同样，日志中的 `Broken pipe` 不能单独充当失败率：消费者在合法终止事件后关闭流也
会产生它。需要联合检查终止事实、请求记账、原始错误、退出身份和最终回执；缺失 usage
仍是未知，不能当零。

安全拒绝保持 terminal UNKNOWN，不重试、不改写请求来绕过它；只有新协议明确允许的
独立 allocation 才可继续。UNKNOWN 阻止性能晋升，不是“无关数据所以可以删掉”。

## 6. 下一步顺序，不能被中途成绩改写

1. **完成当前冻结的 36 个 allocation。** 不换方法、不补跑到赢、不混入旧分数。
   若发生故障或拒绝，保留其原始结局，遵守已冻结的处理规则。
2. **按每题两次固定重复计算均值。** task-Pareto 要求没有题均值退步且至少一题严格
   提高；全 ties 不晋升，并继续保留安全、已得满分及完整开发/确认保护。
3. **先解释差距，再设计新干预。** cohort 关闭后审计公开工作轨迹；私有评分和测试
   细节不向尚在运行的 solver 反馈。把机制故障、工作连续性和方法选择的证据分开。
4. **新实验从 R2 的可执行约束做有来源的删减或替换。** 每个新干预单独冻结、保持
   runtime 和其他坐标不变；不一次同时更换 kernel、提示词、工具和评价规则后归因。
   R2 是否作为下一轮基础方法，仍由完整证据决定，不在本轮悄悄切换。
5. **保留识别边界，再考虑 RSI。** 旧 V1 二进制的系统比较需另行匹配并披露不同工具/
   runtime，不能拿本次方法对照替代。曝光九题也不能替代新确认集。Test-time RSI 仍后置。

当前最重要的判断不是“内核已经更强”，而是：**责任可以更清楚，执行可以更可靠，
但任务能力必须另用真实结果证明。最小化的是 kernel，不是必须把有效方法压到最短。**
