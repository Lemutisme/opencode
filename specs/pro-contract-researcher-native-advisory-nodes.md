# 原生 advisory review：重要节点与 reviewer 强度（设计草案）

日期：2026-09-29，定稿于 2026-09-30。状态：定稿，未实施。第 2 版吸收了 Codex 审查意见；Principal 已确认两项取舍：交付前节点的缓存键纳入执行者声明（第 4 节），以及 context 变化后 review 不可用的既有限制在本轮保留（第 3 节）。本文在[收敛修订稿](pro-contract-researcher-native-advisory-revision.md)和[实施报告](pro-contract-researcher-native-advisory-implementation.md)之上增加两个触发节点和一条 reviewer 配置规则；已实施部分的设计不变。

## 1. 背景

2026-09-27 的 SBNO 行为冒烟测试中，两组 Researcher（`gpt-5.6-luna`，`reasoning_effort: low`）分别在 108 秒和 70 秒内交付，只读了 2284 行原文档中的一部分。开启组看到了能力说明，工具也可用，但没有请求 review；其自述偏差与任务明确要求冲突（未训练 velocity loss，a/b 混用被统一为 b）。单次运行不支持效果推断，但说明"只靠 Researcher 主动请求"在当前模型条件下不足以让 reviewer 进入研究过程。

## 2. 定位

- ProContract 保证长任务执行的完整性：责任由独立 contract 保存，进度由独立 kernel 依据 contract 判断，最终认可属于 Principal。它不保证 Researcher 做得对。
- reviewer 是 Researcher 的第二意见，目的是提高做对的概率。它不参与责任、进度判断或认可。
- 因此交付后为 Principal 做审阅不属于本设计。以后如需要，作为独立的 Principal 辅助另行设计。

两条平衡原则：

1. **只提建议，决定权在 Researcher。** 任何 review 都不得使任务难以推进或收敛。
2. **何时启动：** Researcher 认为需要时启动；在重要节点上可以由任务设置要求启动。

## 3. 触发方式与兼容规则

| 触发 | 时点 | 说明 |
| --- | --- | --- |
| 主动请求 | Researcher 调用 `contract_request({kind:"review",payload:{}})` | 已实现，不变 |
| **交付前节点** | attempt 内尚未发生过交付前审阅时，调用 `contract_report_ready` | 新增，见第 4 节 |
| **中途节点** | 计时满 `afterMs` 后，下一次通过的 `contract_check`，且快照与上次审阅不同 | 新增，见第 5 节 |

不做计划阶段节点：原生路径上无法可靠识别"读完文档、形成计划"，做它需要重新引入计划协议。

**节点策略随登记持久化，带显式版本：**

- 新登记保存 `nodes: { version: 1, submission: boolean, midcourse?: { afterMs } }`。签发 API 的默认值为 `submission: true`、不开启 midcourse，但写入存储的是显式值。
- 可以关闭交付前节点而保留主动请求。
- 旧登记没有 `nodes` 字段，一律按"只有主动请求"处理，不能把缺失解释为开启。登记仍不可重新配置。
- 关闭 review 的合同、历史模式和 required 模式的行为都不变。

登记绑定签发时的识别 context，这一既有限制保持不变：challenge、Principal resume 或修订改变 context 后，该合同的所有 review 触发都不再可用。本设计不放宽 `sameTask`；跨 context 重新登记需要另行设计授权规则。

## 4. 交付前节点

**时点与计数：**

- 以 binding 的 attempt 编号计数。同一 attempt 内换 Session 或 generation 增长，不会重置机会。
- 机会只在一次审阅被**成功接纳**（即发生了暂停）时才算用掉。因忙、时间不足、缓存命中或接纳前出错而放行的调用，不算用掉。
- 例如：第一次交付因忙被放行，replay 失败没有形成交付，修复后再次交付，这时仍会尝试接纳审阅。
- 接纳后 reviewer 超时、不可用或意见不完整，也算用掉；按已有规则恢复并投递不可用说明。
- 原生 `completed` 结果产生的新 attempt 不改变 context，所以会重新获得一次机会。

**位置：**钩子位于 native `contract_report_ready` 的授权检查和 native 分支确认之后、action 预留和 replay 之前。

**接纳成功时：**

1. 宿主按方案 A，在同一事务内完成：核对授权和时间，检查其他 pending／running 工具，查询缓存，写入请求记录，写入节点使用记录，写入规范化后的 `summary`／`uncertainties`，以 CAS 关闭 admission。
2. 工具返回"交付尚未记录，按任务设置正在进行一次独立审阅，执行将暂停"。这次调用不做 replay，不发出 report-ready 命令，不消耗 action。
3. 审阅材料在原登记材料之外，加入这次提交的 `summary` 与 `uncertainties`，标注为不可信的执行者声明，供 reviewer 对照代码核查。
4. 同一可信调用的精确重试返回同一个决定。

**恢复消息：**仅在同 Session 恢复时投递，写明：

- 这是任务设置要求的审阅，不是 Researcher 请求的；
- 交付尚未记录；如果仍决定交付，再次调用 `contract_report_ready` 即可，不需要修改任何内容，也不需要回应意见；
- 原 `summary` 和 `uncertainties`，便于原样重新提交；
- 意见全文，或者不可用的原因。

如果按既有的崩溃恢复规则换到新 Session，则继承已有限制：由原 brief 接手，不注入旧意见和原提交内容，只保留在宿主记录中。

**放行与失败规则：**

- 接纳事务提交**之前**的任何失败（忙、时间不足、缓存命中、宿主出错），本次调用继续走原生交付，并记录"强制审阅未发生"及原因。
- 接纳事务提交**之后**，以已持久化的请求为准：无论钩子后续是否正常返回，都按已接纳的请求走现有的暂停和恢复。钩子返回丢失时，Core 继续原路径会因 admission 已关闭而失败，不会产生交付；随后由恢复消息说明情况。
- 中断和授权失效必须如实传播，不能当作"继续"处理。

**缓存：**交付前节点的缓存键在原有内容之外，加入规范化的执行者声明。

选择这种做法的理由：节点的目的是在交付前审阅"本次要交付的内容"，其中包括声明。如果代码没变、但总结里新增了没有依据的结论，只看快照就会错误命中缓存。代价是：一次没有声明的主动审阅，不能替代交付前节点，每个 attempt 最多因此多一次暂停。

## 5. 中途节点（可配置，默认关闭）

**计时：**

- 起点取两者中较晚的一个：attempt 开始时间，或最近一次被接纳审阅（任何触发方式）的开始时间。
- attempt 开始时间由宿主在首次观察到新 attempt 编号时持久化记录。宿主重启不会重置计时。
- 缓存命中和未被接纳的尝试不重置计时。被接纳但结果不可用的审阅会重置计时，因为暂停已经发生。

**触发：**计时满 `afterMs` 后的下一次 `contract_check` 通过，并且快照与上次审阅不同时，宿主按方案 A 尝试接纳。频率由 `afterMs` 控制，不设次数上限。

**check 结果：**

- 接纳时，工具在原输出上附加"按任务设置开始一次独立审阅，执行将暂停"。
- 由于工具执行期间仍可能被中断，这里只保证 replay 结果和证据引用被持久保存，不保证 Researcher 能即时收到工具回执。
- 同 Session 恢复时，恢复消息补送 check 结论（是否通过）和证据 hash。换 Session 时按既有限制不补送。
- 不接纳时，check 结果不受影响。接纳事务提交前的宿主错误不影响 check。

## 6. reviewer 强度规则

**原则：**reviewer 默认继承 Researcher 的模型，推理强度不得低于 Researcher，推荐高一档。档位按 `none < minimal < low < medium < high < xhigh < max` 比较。

**只按最终生效的配置比较：**

- variant 名称本身不代表强度；variant 为 `default` 或省略时，使用模型自身的默认配置。
- SDK 登记时，只有当双方为同一模型、且都能解析出最终生效的推理强度时，才执行比较。能确定更低时拒绝登记；能确定不低于时记为"已确认"。
- 无法解析时，登记可以进行，但在签发回执和附件中标为"强度未确认"并写明原因，不能标记为"已确认"。
- 换用其他模型需要显式指定并记录理由，不做自动强弱判断。

**评测环境：**可信角色路由会最终覆盖模型和推理强度，所以以网关路由配置为准。启动方案须核对并冻结 `worker` 与 `reviewer` 两条路由的参数。

**下一轮试运行：**

- Researcher `low`，reviewer `high`。
- 两个时限需分别确认并在运行前冻结：`reviewMs` 限制整个 reviewer job，网关的 15 分钟限制针对单次 provider 请求。调整前者不影响后者，high 档的单次请求需能在 15 分钟内完成。

## 7. 收敛保障汇总

- 意见从不作为 check 或交付的条件；不要求逐条回应或完成声明。
- 交付前节点每个 attempt 最多接纳一次；接纳前遇到障碍直接放行。
- 不自动重复审阅，不重审到"同意"为止。
- 单次审阅有时长上限；接近 deadline 时不启动。
- 其他工具运行时不暂停；恢复消息明确可以直接交付。

## 8. 实现范围

**Core（执行适配层）：**

- `ProContractDelivery.Handler` 增加可选的节点钩子，输入为执行身份、可信调用身份、节点类型（`submission` 或 `check`），交付节点附带 `summary`／`uncertainties`，check 节点附带 replay 结果引用；只返回"拦截"或"继续"。
- native `contract_report_ready` 在第 4 节指定的位置调用钩子；拦截时返回未记录的结果和说明，继续时走原路径，逻辑不变。
- `contract_check` 在得出结果后调用钩子；拦截时在原输出上附加说明。
- 钩子缺失时一律视为"继续"。未登记合同行为不变。

**SDK：**

- 登记配置增加带版本的 `nodes` 策略和 reviewer 强度检查。
- 方案 A 的接纳逻辑接受 `contract_report_ready`、`contract_check` 作为发起工具（目前只接受 `contract_request`）。
- 请求记录增加触发类型；节点使用记录按 attempt 保存，并与接纳在同一事务中写入。
- 交付前节点的缓存键加入规范化的执行者声明。
- 恢复消息按触发类型区分措辞，并补送交付前节点的原提交内容和 check 节点的结论。
- `NativeAdvisory.guidance` 增加一句说明交付前节点，改动后的 brief 需重新经 Principal 批准。

**不做：**交付后的 Principal 审阅、计划阶段节点、不暂停的并行审阅、跨 context 重新登记、逐条回应、累计上限。

## 9. Change gate（Core 钩子）

这两个钩子不承担 kernel 不变量。executor 不能使自身完成具有权威性，这一点由 kernel 独立保证，与钩子无关。钩子的定位是执行适配层的调度入口：让可选的宿主在两个原生工具产生副作用之前介入，用于安排建议性审阅。触发策略、计数、缓存和强度规则都留在 SDK。

| 项目 | 说明 |
| --- | --- |
| 必须保持的边界 | 钩子只能返回"拦截"或"继续"。它不能修改 replay、快照或交付内容，不能自行记录交付，不能消耗 action 或 turn，不能改变授权 |
| 没有它的反例 | 宿主无法在交付记录生成之前介入。只能事后轮询发现 check 或交付，此时要么模型已经进入下一回合，关闭 admission 会截断正在进行的回合；要么交付已经发生，交付前节点无从实现 |
| 为什么现有组合做不到 | native `contract_report_ready` 与 `contract_check` 都不经过 delivery handler；唯一的现有宿主入口 `contract_request` 依赖 Researcher 主动调用，而试运行已证明这一前提不足 |
| Pure-kernel 验证 | kernel 与 reducer 不变；现有 constitution 与 pro-contract 测试继续通过 |
| 边界验证 | 见第 10 节 |
| 增删概念 | 新增可选节点钩子与触发类型；无新增研究状态机、回应门槛或累计上限 |

## 10. 验收建议

**交付前节点：**

- 第一次交付被拦截并恢复，第二次交付正常记录；不修改任何内容也能交付。
- 四种接纳前放行情况各自直接交付，并且不用掉机会。
- 第一次放行、replay 失败、修复后再交付时，仍会尝试接纳审阅。
- 同一 attempt 内换 Session 后，机会不会重置；原生新 attempt 重新获得一次机会。
- 接纳事务已提交但钩子返回丢失时：不产生交付，按已接纳请求暂停和恢复。
- 同一份代码、不同的总结时，缓存不命中。
- 中断和授权失效如实传播。

**中途节点：**

- 默认关闭时 check 行为不变。
- 开启后按计时和快照变化触发；缓存命中、接纳失败的审阅、宿主重启对计时的影响符合第 5 节。
- check 工具返回前被中断时，replay 结果仍然持久保存，并在同 Session 恢复时补送。
- 接纳前宿主出错时 check 不受影响。

**兼容与强度：**

- 旧登记缺少 `nodes` 字段时只有主动请求；关闭交付前节点后主动请求仍可用。
- 能确定 reviewer 更弱时拒绝登记；无法解析时标为"强度未确认"。
- 试运行配置中 `reviewer` 路由为 high、`worker` 为 low，两者冻结。

**回归：**原有 245 项测试、网关测试及两条确定性演练重新通过。

**试运行：**两组都重跑（每组实际只需数分钟），关闭组作为同一代码下的基线；开启组预期至少发生一次交付前审阅。
