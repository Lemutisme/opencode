## 3. 版本与兼容边界

采用一个新的宿主协议判别值：`manifest.reviewPolicy={version:3,plan:"advisory",delivery:"advisory"}`。它同时选择本文的宿主关联、独立提交和可选回应语义，不再叠加一个默认强制修复生命周期。可选回应／意图／完成记录使用 v3 的记录格式；不要求发行方选择它们才能使用默认流程。

## 4. 宿主绑定身份，模型提交研究内容

### 4.1 两层输入与有限视图

宿主持久化完整信封：Contract、当前 revision/specHash/manifestHash、execution/session/admission 身份、run 版本、plan 版本与 hash、candidate、review job/outcome、材料清单、引用 map、证据来源、原 deadline。模型负责研究内容、动作选择和可选的理由，不负责生成或修正这些身份。

每次提供可执行的计划／候选／反馈视图，宿主存储不可变 view，绑定**实际授权的 execution 和当时材料**。模型可见一个短的、不可自行构造的 `view` 选择对象及带说明的目标／证据选择器；完整 hash 留在宿主记录。若现有执行接线能可信地携带该具体 admission 的 view，工具直接注入；否则 payload 必须回传所给 view 对象。不得从“当前 session 的最新 run”猜测旧调用所见材料，不能为省一个字段失去并发防护。

最小实现允许一次已授权视图内的动作使用同一只读 view；任何 plan/candidate/outcome 集合变化都使相应写动作的前置版本失效。view 是校验输入，不是扩权凭证。长历史通过按需只读接口取回，保留全部原文和证据的可恢复性；正常 prompt 不重复整份制度账本。首片返回完整按需视图，尚无分页；不能以此宣称解决了长历史规模问题。视图、读取和原始模型调用均可审计。

材料适用性与审计追加序号分开。单纯追加一条说明不应使未变的候选视图失效、迫使模型每写一条记录就刷新；同一目标的声明仍须检查前驱，冲突不能覆盖。数据库保存继续比较当前行版本，但不能把所有无关审计追加都变成重新 review／验证的理由。

### 4.2 不同动作的绑定

| 模型提供                                 | 宿主绑定和校验                                                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 计划内容、原授权内选定的输入路径／选择器 | 授权、下一个计划版本、agreement、准许路径的实际 hash；与 view 中输入快照一致。原受保护输入改动不能借重新 capture 合法化。 |
| 对某条意见的简述或部分逐条回应           | 选择器解析为精确 `outcomeHash + findingID`，保留该意见的原材料版本；同名 finding 不视为同一意见。                         |
| 可选意图／完成／纠正声明及证据选择器     | 精确原目标、前一声明、当时计划／候选／实验／验证，以及当前适用性。无意图也可附证据说明实际变化；不能强制先补造意图。      |
| 实验、继续工作、候选准备／提交           | 实际授权、期望 run/view 版本、当前计划与候选、正式实验及验证证据；提交动作不依赖回应。                                    |
| Reviewer 的材料／证据选择器              | 只解析该 job 的不可变映射。继续使用宿主生成的合法对象；未知、歧义、跨 job、候选或版本引用拒绝，旧错误 hash 不猜补。       |

原始 payload、宿主绑定信封、map 与解析结果分别保存。旧意见在新候选的交付包中仍是“历史意见”；可以附上针对当前候选的补充说明，不能修改其原目标、假称已评审当前材料或复制旧 accept 作为新支持。

### 4.3 时序、并发与恢复

动作先核对真实授权与 view，完成证据 I/O 后再次核对授权、原 deadline 和期望版本，再用既有原子比较／保存边界提交。两个相同前置版本的冲突修改只能一个成功；仍在有效授权内的精确工具调用重试返回原 receipt，同一调用身份不同 payload 拒绝。成功重试不重复实验、评审或候选提交；不能用内容相同推断是重试。

S1 接线补充（2026-09-21，依据 review 指出后核实）：canonical Tool.Context 已有 `assistantMessageID` 与 `toolCallID`，原 `contract_request` 转交 handler 时丢失它们。通用转交边界新增可信 `call:{messageID,callID}`，也用于候选准备请求；由工具实现从 context 注入，模型 payload 不包含调用身份。研究宿主用 `execution.contractID + execution.sessionID + call.messageID + call.callID` 索引 durable receipt，另外核对原 execution、kind 和完整 payload。不同 message／call 的相同内容是新调用。记录与状态修改同事务提交，拒绝另留审计事件而不修改 run。旧 handler 可忽略新增元数据，v3 缺失它时明确拒绝，不生成随机替代身份。

调用身份、执行授权与材料 view 是三个独立条件。动作关闭 admission 后，旧工具上下文仍被 Core 原有 fence 拒绝；不得为返回 receipt 重新开放权限。已完成调用可由受信宿主读取原 receipt；这不是自动重执行／崩溃恢复。A6 必须同时验证相同调用精确重试、相同调用不同内容冲突、新调用相同内容，以及关闭 admission／过期执行无法借 receipt 扩权。

这项 Core 边界增量只传输已有通用调用身份，不改 reducer 或研究语义。对应 constitution 的 exact identity、auditable rejection；缺少它，研究层无法区分相同内容的新调用和重试。边缘无法从现有 handler 参数可靠恢复 tool call，故需要这一次透传；纯 reducer 无新分支，保留原 kernel 回归，新增 canonical tool 到 handler 的真实边界测试，并在宿主用持久化 receipt 测幂等／冲突。新增概念仅为两字段调用元数据，删除内容相同即重试的实现可能性，不增加授权类别。

错误返回稳定代码、出错字段、可读原因、适用协议和合法的下一动作。例如：

| 错误                                                               | 恢复方式及不变项                                                                                                              |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `invalid_payload`／`protocol_mismatch`                             | 按冻结版本给出正确字段及最小示例；保持当前执行 admission 可用，修正后再提交。不能先落成半条回应，也不能转用旧 schema 的报错。 |
| `stale_view`／`state_conflict`                                     | 返回刷新入口；读取新视图，Researcher 重新选择动作。宿主不自动把旧意见、证据或提交请求绑定到最新材料。                         |
| `unknown_reference`／`wrong_owner`                                 | 指出不可接受的选择器和当前合法对象来源；拒绝该引用，保留原请求。可以改选合法引用或不提交这条可选记录。                        |
| `candidate_changed`／`verification_required`                       | 返回实际缺少的硬前置条件；重新准备／实验／验证当前候选，旧证据仍归原候选。不能补改旧 hash。                                   |
| `authority_expired`／`deadline_expired`／`scope_requires_revision` | 不允许通过重试、刷新 view、换 Session 或增加声明恢复授权；保留真实状态，按原外部授权／终止路径处理。                          |

普通 schema 错误和无效的可选审计记录不关闭工作许可、不自动标记整个 run unavailable，也不要求 Principal 批准普通修正。可恢复指“原权限和时间仍有效时可以纠正”，不保证模型一定会纠正，更不延长 deadline。所有接受／拒绝动作仍有不可变记录，拒绝不改变研究物化状态。

## 5. 默认流程及硬边界

### 5.1 研究动作与评审记录正交

```text
计划内容 -> 宿主绑定 + 机械计划准入 -> 计划 review 检查点 -> 执行
   ^                                                        |
   +---------- 任务内计划修订 <-------------------------------+
执行 -> 正式实验 -> 候选准备 / capture -> 验证 -> 候选 review 检查点
   ^                                                    |
   +-------------------- 继续研究 / 修订 -----------------+-> 候选决策
                                                            |
                                     独立 submit + 再 capture / 硬检查
                                                            |
                                                Core handoff -> ready
                                                            |
                                                 外部 exact recognition

意见 / 简要说明 / 可选逐条回应 / 意图 / 完成声明：追加审计记录，不作为上述箭头的门票
```

“机械计划准入”不表示计划科学正确。Researcher 决定方法、数据使用或诊断保留状态改变时，仍应在原授权内修订计划，再按新版本执行和验证。单纯修正文案或回应建议不要求一套修复生命周期。已声明的变化、计划版本与实验归属由宿主检查；计划与代码语义是否一致仍需证据和独立判断，不能假装宿主可从自由文本完整判定。

首个实施切片复用串行宿主，**不增加后台并发 review 编排**。固定检查点为新计划准备执行前、当前候选验证后：宿主保存不可变材料并请求一次独立 review，在预先规定的单次操作期限及原 deadline 内收集结果、停止和清理该 job。检查点的存在可被审计，但“有有效报告／accept／回应”不是 v3 准入条件。禁止模型为继续工作再填写“我已读”或 skip 表单。

每个检查点记录材料身份、状态与收集截止。迟到输出仍归原 job／材料，另作追加证据；不追改已封存交付包、不悄悄恢复旧 accept，也不把同一意见绑定到随后出现的候选。deadline 到期后的归档和清理不是继续研究的授权。

计划检查点结束后，宿主自动恢复该计划的执行权限，连同可用意见或真实不可用原因。候选检查点结束后，提供独立的 `submit_candidate` 与 `resume_work` 动作：前者只需明确提交当前候选，后者返回原授权内的研究或计划修订。两者均不需要 `review_response`、逐条 reason、意图或 completion。简要处理说明可以随提交提供，也可此前追加；缺省时由宿主写 `not_provided`，不替 Researcher 撰写理由。

上述动作是研究 handler 协议，不是新增 Core command。候选准备与最终提交含义在模型接口中明确；现有拦截式候选准备接线可以复用。最终必须有 Researcher 的明确候选提交意图；仅仅停止输出、报告缺失或宿主允许提交，均不能被当成自动成功／提交。提交动作可直接使用当前有效候选视图，无须先做任何评审回应。final-only 任务沿用相同候选边界，但不要求不存在的计划或正式计划实验。

候选决策阶段可暂时只读，以防归档后漂移；`resume_work` 直接恢复已授权能力，不要求先把某条意见标为 repair。再次提交要绑定实际候选并满足原验证规则；旧实验不能支持新代码，新旧 review 严格区分。宿主不替 Researcher 修改计划、修复代码、选择认可结论或根据评分真值决定动作。

### 5.2 不可用与证据不可信分开

- Reviewer 拒绝、给出 P1、scope unclear 或建议增补实验，作为意见保留。没有事先约定的机械规则与证据，不转成停工条件。严重级别 P1 与校准用例 P1 分开。
- Reviewer 格式错误、无输出、超时或引用错误，保存 raw/capture/map/error 与真实 `unavailable`，检查点仍可结束。启动失败也要有 checkpoint failure，不能因没有 outcome JSON 就卡在 feedback。`pending`／`not_requested` 不填成 available，也不成为对旧 accept 的替代。
- 只要隔离与清理已确认、核心授权和证据有效，单纯没有可用评审不阻止继续或提交；不自动反复评审直到 accept。对新的实际计划／候选保存新检查点，与重试旧意见不同。重复同一请求必须幂等。
- 无法确认 job 停止或共享隔离安全时，记录独立的 infrastructure 状态并阻止会冲突的动作。首个串行切片按既有安全清理规则等待／终止，不以 advisory 绕过正在运行的写入者或跨 deadline；不能把这类停顿说成 reviewer 否决。
- 核心候选、正式实验、验证、授权或来源链损坏，拒绝依赖它的操作。收到的评审本身不可解析，可以如实归档；**一个已归档对象后来 hash 不符**是完整性问题，不能抹成“未回应”或“报告不可用”。最小切片保守阻止依赖该损坏 bundle 的发布／认可并暴露恢复所需证据；不新增默默删除坏对象的旁路。
- 可选审计请求被拒绝时，没有该有效记录本身不妨碍提交；若连拒绝事件、材料或交付封存都无法持久化，属于存储／审计基础设施失败，不能伪造完整交付。

### 5.3 Constitution 对应关系

| 约束                                          | 本设计保留的边界                                                                                            |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Obligation conservation / residual control    | 模型停止、review unavailable、无候选、评分失败均不清偿任务；超出任务范围仍交外部 Principal 修订。           |
| No self-certification                         | Researcher 的回应、完成声明与 ready 都只是报告／候选；最终认可、release、discharge 仍由规定的外部权限执行。 |
| Exact identity / effect authority             | 宿主从真实授权及不可变 view 绑定，重新核验候选、证据、当前 revision 和原 deadline；受保护输入及权限不放松。 |
| Responsibility closure / historical integrity | 原 challenge 及依赖责任传播保持；新协议、纠正记录和派生分析不删除旧意见、attestation、失败或评分。          |
| Auditable rejection / frontier-relative quiet | 拒绝不改变物化状态，接受／拒绝可追溯；可提交或评分完成不创造新的 quiet 状态。                               |
| Capability-shaped projection                  | 只向模型给可采取动作所需的任务材料、意见与选择器；完整制度身份由宿主保存和执行。                            |

研究策略、计划、review 和测量留在 research 宿主／research-eval。没有理由在 Core 加科学判断、反馈完成率或评测揭盲规则；若后续确需 Core 变更，另按 constitution 的 change gate 逐项证明，不能以本设计代替。现有部署的合作式隔离不因减少 hash 输入而变成强安全沙箱。

## 6. 交付与实际修复事实

v3 交付包分别包含：原约定及当前计划／候选／正式证据、宿主准入和明确提交记录、每个检查点的原始 review 状态与意见、已有处理说明及可选记录、未回应／未完成／分歧清单、来源与计量状态。所有检查点都有记录；有原文就保存原文，未取得原文则明确 capture 状态，不造出 reviewer 内容。

意见以原 outcome 和 finding 为键；无可解析 finding 的 unavailable 仍有 checkpoint 级记录。`not_provided`（没给简述）、`unaddressed`（该意见无对应回应）、`pending_intent`（有意图而无后续记录）、`disputed`（保留分歧）、`historical_only`（旧材料记录）分别呈现。通用简述不能自动算逐条回答；未回应不能推断为同意、未修复或没有读过。宿主可生成这些机械缺失标记，不能生成 Researcher 立场。

实际变化、Researcher 声明和独立验证是三类来源：

1. 宿主保存绑定版本的代码／计划差异、正式实验及结果。没有 response 或 completion 也保存这些事实，不在查询中按 responseHash 过滤掉。
2. Researcher 可追加声明与纠正，原声明保留。普通建议可简短说明取舍，不必先声明意图再关闭意图。完成声明不能凭存在就生成“修复成立”。
3. 独立判断根据实际前后代码、方法与可执行实验确认修复／删除／未变化及适用范围；将判断与证据单独归档。允许 `actual_repair=confirmed` 与 `completion=absent` 同时成立，也允许 `claim=fixed` 与 `actual_repair=unsupported` 同时成立。科学判断不是宿主给出的新准入资格。

可选诊断的合规删除单列为 removal，不算实现选参与评估分离。原本满足要求时，没有“新修复”；有依据不采纳、合理保持方案与不提供说明也各有不同的处理／审计结果。后续的新材料或独立判断是带来源的追加记录，不能修改已封存候选或假装是提交时已知证据。

## 7. 未来测量与实例隔离

### 7.1 四个报告维度

| 维度           | 依据及输出                                                                                                                     | 不允许的替代                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 研究结果正确性 | 候选材料、独立实验与任务标准；correct / incorrect / indeterminate；无候选另记 not_submitted，仍留分母。                        | 不以 reviewer accept、ready 或审计齐全代替正确。没有候选不造质量分。       |
| 意见处理质量   | Reviewer 判断作为单独子项；Researcher 实际采纳、修复、合规删除、有据反驳、合理不采纳、无据退让、未处理分别评价，并绑定原意见。 | 不抹掉误拒，不把脚本写的回应算模型能力，不以 completion 缺失取消实际修复。 |
| 审计完整性     | 原意见／曝光、简述、逐条回应、意图、计划版本、声明／纠正、证据关联及缺失原因逐项记录。哪些为可选、适用与否由 rubric 预先区分。 | 可选项 absent 不自动等于研究缺陷；mandatory provenance 缺失不能伪装可选。  |
| 基础设施状态   | 发行／停止阶段、清理、候选是否可知、证据／封存、评分可用性、传输日志恢复、原账本／补记／未知用量。                             | 超时不证明已停，补记不证明操作成功，派生已知总数不称完整计量。             |

每个适用细项同时带机会与证据状态：`not_observed` 表示相应事件没发生；`not_applicable` 表示该动作对该意见不适用；`insufficient_evidence` 表示相关事实有待判定；`not_scored` 表示评分未开展／未完成。缺失、null、无机会不累计成产品缺陷。具体真值和阈值在新批次冻结前定义；本次不重标任何旧值。

P1 原探针继续只测 reviewer 判断；真实 Researcher 后续行为单独取证。保留 validation 选参／test 评估与 test 选参／同一 test 评估的真实执行关系、措辞变体及 ID／索引干预，不硬编码“好计划必须接受”，不删除坏例或重标历史真值。无误拒、无 unavailable 或无修复机会都记为未观察到，不额外重跑制造机会。新协议、提示、场景或揭盲规则构成比较条件变化，必须在新批次报告中列出，不能将跨轮差异直接归因为模型提升。

### 7.2 每实例封存与揭盲

未来 `instance-isolated:1` 将门槛改为**目标实例与评分上下文的条件**，不再遍历全部实例的 terminal/candidate seal。保留预登记的总分母、配置身份和不可变事件记录；每例追加独立的封存／评分状态。原始 cohort 事件链仍验证其真实内容，其他实例的评分失败不等于事件链被篡改。

| 单例状态                                   | 本例反馈评分                                                                  | 其他完整实例                                                     |
| ------------------------------------------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 有候选且两位独立候选评分／必要裁决已封存   | 允许按本例明确 reveal receipt 揭盲。                                          | 不需等待本例以外的 seal。                                        |
| 已证实无候选且失败／截止材料已封存         | 无候选质量分；可评价有证据的意见处理，缺失仍披露。                            | 不受阻。                                                         |
| 候选存在但双评／裁决不可用，或本例封存失败 | 规范反馈评分保持 blocked / not_scored，记录原因与已知证据；不以“缺候选”绕过。 | 不受阻；批次结果标 partial，不能叫完整校准。                     |
| 候选有无不明、清理未确认或材料损坏         | 不造 absent seal；本例 dependent judgments 不可做，按可信证据保留 unknown。   | 仅共享完整性／安全边界受影响的实例停下，必须说明影响范围和依据。 |

最小版本不为了“分析本例”绕过该例自身的独立评分门。必要的工程排障可在单独、明确非盲评的操作上下文读取材料，不能把排障意见冒充候选评分。这样一例封存失败仍可能使**该例**未评分，却不能让其他合格实例永远等待它。

启动前预登记两位独立评分者、独立裁决者、材料 allowlist、上下文身份及不可用方案。每个实例的候选评分上下文只见该候选与冻结标准；意见、回应和完成声明必须隔离在反馈包中。候选评审 A/B 分别封存后，必要裁决使用独立上下文并封存；再由专用反馈评分上下文 A/B 读取轨迹。**收到任一实例反馈的上下文，不能随后参与任何该批次尚未封存的候选盲评或候选裁决。** 同一操作者或上下文换名字不算隔离。

可以用全新上下文为其他实例独立评分，不把已揭盲内容传入；每次材料授予都保存身份、范围和 receipt。评分者不可用时按冻结替补规则使用未污染的独立上下文并保留原失败，或将本例标 not_scored；单人意见不能冒充双评，不反复评分择优。当前合作式访问限制及同一模型家族等局限如实披露；若未来不能证实上下文隔离，该批次不能使用本揭盲策略，不能临时降低独立性要求。

候选自身若包含 Researcher 写入的评审内容，不能为了“盲评”删改候选。记录这种实际曝光，并按预先冻结规则标记盲法受限或该项无法取得盲评；不能把内容已曝光的判断称为完全盲评。宿主独立保存的评审／回应／完成记录则始终留在候选阶段的材料 allowlist 之外。

发行隔离也按新冻结策略执行：局部进程已停止、资源隔离确认的单例故障不阻止其他例的一次原定尝试；凭据／隔离破坏、共享源码漂移、共享存储损坏或无法排除的在途进程冲突，暂停依赖该共享资源的范围。原因不明不等于安全。不得为失败例延长原 deadline、补发尝试或临时放宽停止条件。

第七轮保持 `candidate-or-terminal:1` 与整批门的原失败。未来若另做归档派生分析，另建分析 ID、来源 hash、所用新代码／rubric／揭盲协议、评分者先前曝光及不能盲评的限制；不得写回原目录或冒充原轮第二阶段已完成。本次没有启动这样的派生分析。
