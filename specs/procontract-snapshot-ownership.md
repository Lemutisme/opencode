# Snapshot object ownership and retained subject locations

This candidate addresses two different dependencies on mutable candidate Git metadata. It is isolated on `snapshot-ownership`, based on `ea5947926553d27c5b32c57c79add04ba2abfc4c`; it does not change the currently frozen ProgramBench runtime or any historical result.

Previously a snapshot repository copied the candidate index and borrowed `/candidate/.git/objects` through Git alternates. Deleting or replacing `.git` could make an already captured tree unreadable. Separately, a new process resolved Project identity from the candidate's current Git repository and derived its snapshot path from that identity. Reinitializing Git with a different root commit changed the path, even when the original snapshot objects still existed. A replay in the original Location context could therefore succeed while a later independent export failed.

New snapshot storage explicitly dissociates its seed: it copies the index, writes the seed tree, imports index-reachable objects with Git repack, then removes the alternate dependency. The import is performed once when initializing the private store, not on every provider turn. Repack has a bounded individual timeout. The fully initialized repository is renamed from a unique staging path; a failed import cannot publish a usable `HEAD` at the final path. Temporary storage is cleaned on failure. The new `.owned` namespace preserves preexisting borrowed repositories instead of silently relabeling them as self-contained.

A successful capture also publishes a private reference indexed by canonical Location directory and subject hash. Its versioned record contains the exact captured hash, Location directory, and native repository identity. A temporary file and an exclusive hard link publish the record atomically across process boundaries; this is not an fsync guarantee against power loss. Repeated captures validate the existing reference and cannot redirect the first publication. All readers that take snapshot IDs resolve this record, validate subject and Location identity plus physical containment under native storage, and read the retained repository. They do not resolve a replacement subject from the live workspace, search arbitrary project stores, or change the Contract handoff. Malformed or mismatched records fail. An explicitly disabled snapshot configuration still blocks materialization. A retained record can be materialized after candidate Git metadata is removed or recreated.

Legacy captures lack these references. Readers retain only their original exact namespace lookup when it is still resolvable; they do not reconstruct already lost objects or guess a Project identity. Cross-store comparison and selective restore import the requested tree closure into one of the resolved native stores through a bounded local Git fetch, without persistent alternates, refs, or FETCH_HEAD. Existing stores are neither deleted nor relabeled. This does not promise that legacy caches are wholly read-only: normal undo operations can update their index, as before, and cross-store reads can add object packs. No frozen cohort is modified. Tests cover forward and reverse comparisons, selective preview and restore, and checkout across legacy and recreated storage.

Snapshot capture remains best effort for Session history: a real Git index-lock failure returns `undefined`, and a later successful capture returns the current tree. Contract check and handoff already reject an unavailable capture. No previous subject is substituted. Handoff/replay/export failure classification in the Python runner is outside this runtime patch.

Validation uses actual Git repositories and the real Snapshot, ProContract replay, and export services. A separate compiled CLI process exports a persisted handoff after Git reinitialization. The old binary reproduces replay success followed by an export error; the candidate exports the same frozen subject even after the live file has changed. These tests establish mechanism behavior, not ProgramBench semantic-score improvement. No model or hidden grader is used.

The candidate does not change solver policy, native SessionRunner ownership, provider requests, tool schemas, Contract authority, deadlines, cumulative-count semantics, or delivery claims. Future cohorts require separate source/binary freezing and qualification; existing frozen cohorts and failed records stay unchanged.
